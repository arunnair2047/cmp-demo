Network Intelligence Initiative

Telecom networks react to congestion.
We want them to prevent it.

A concept for an AI-powered congestion management platform that identifies network congestion before customers are impacted — and in cases where patterns are known, prevents it from occurring at all — by taking automated, root-cause-appropriate corrective action.

📡
Congestion is unpredictable and reactive
Network congestion is treated as a surprise event. A football match ends, 55,000 people open their phones simultaneously, and the NOC engineer gets a P1 alert 20–30 minutes later — after customers have already noticed. The industry standard response is reactive: detect, escalate, remediate. By the time action is taken, the damage is done.
💰
Operators overbuild to compensate for unpredictability
Because peak demand is unpredictable, operators provision significant spare capacity as a permanent buffer. This capacity sits idle most of the time. For a network the size of BT or Openreach, this represents substantial avoidable CapEx — capacity that exists purely to handle worst-case scenarios, not the average case.
🔧
No intelligence about what type of congestion it is
Current tools detect that congestion is happening but not why. A crowd surge, a flash viral event, and a degrading antenna all show the same PRB spike on a NOC dashboard. They require completely different responses. Applying the wrong resolution — throttling traffic during a hardware fault — makes things worse, not better.
👥
NOC teams are fire-fighting, not managing
Network Operations Centre engineers spend the majority of their time responding to P1 and P2 alerts rather than proactively managing network health. Each congestion event requires human judgment, manual API calls into vendor management systems, and post-incident reporting. This is unsustainable as network complexity grows with 5G densification.
2
Reactive vs Predictive — The Key Distinction

CMP operates in two modes depending on how much historical data it has for the specific event type. This distinction is the core value proposition — it is not just a faster response, it is a fundamentally different operating model.

Mode 1 — Reactive (unknown events)
⚡
An unexpected event occurs — flash viral content, emergency evacuation, unplanned infrastructure failure
🔍
Isolation Forest detects statistical anomaly on SNMP stream within 1 minute of onset
⚙️
Congestion score crosses threshold — root cause identified — appropriate resolutions fire automatically
✓
Total time from onset to resolution: under 2 minutes. No human intervention required.
Compare this to the current baseline of 20–30 minutes for a NOC engineer to detect, escalate, and manually remediate.
Mode 2 — Predictive (known patterns)
📅
After 6+ months of training data, the LSTM model has seen 52+ previous Friday post-match crowd surges at each cell
🧠
At 17:45 — 15 minutes before match dispersal — the model recognises the building UE count pattern and begins staging resolutions
🔒
Neighbour cells are pre-positioned on standby. Carrier activation is pre-triggered. MIMO boost is applied ahead of the peak.
✓
PRB never crosses the congestion threshold. Nobody knows there was going to be congestion. It was quietly prevented.
This is the long-term value: operators no longer need to provision excess buffer capacity because known peaks are managed in software before they become incidents.

4
How It Works — The Six-Stage Pipeline
📥
Stage 01
Data Collection
PM counter files every 15 min from eNodeB, MME/AMF, OSS/ENM. SNMP traps real-time for threshold events. Raw counters — not KPIs yet.
⚙️
Stage 02
Normalisation
Raw counters converted to KPI percentages. UTC time-aligned across cells. Outliers capped. Clean data enters ML pipeline.
🧩
Stage 03
Enrichment
90-day baselines, event calendar, neighbour cell load added. ML receives deviation from normal — not raw KPIs.
🤖
Stage 04
ML Engine
3 parallel models: LSTM for cyclical patterns, XGBoost for trend acceleration, Isolation Forest for unknown flash events.
📊
Stage 05
Congestion Score
Composite 0–100 score from three models with dynamic weights. Score crosses 80 → resolution cascade begins.
⚡
Stage 06
Resolution
Root-cause-appropriate resolutions fire via network API calls. Right tool for each congestion type. No human in the loop.

5
Six Automated Resolutions — Scenario-Specific

Not every resolution applies to every scenario. The system selects only the actions that address the actual root cause. Applying the wrong resolution — throttling traffic during a hardware fault, activating a slow carrier for a 10-minute flash event — actively makes things worse.

R1 — Cell Handoff
520 UEs migrated to neighbouring cell via X2 A3 handover. Under 300ms interruption per UE. Effect in 30–90 seconds.
Applies: Crowd surge (primary), flash events, partial for degradation
R2 — Band Upgrade
Reserved 2600MHz carrier activated on same cell. Pre-configured but dormant. Broadcasts via SIB. Effect in 2–5 minutes.
Applies: Crowd surge, degradation. Not flash events — too slow
R3 — Capacity Boost
TX power 43→46dBm. MIMO layers 2→4. Scheduler weight +20%. Software only — no hardware change. Effect in 60 seconds.
Applies: All congestion scenarios. Primary for infrastructure degradation
R4 — Dormant Cell
Locked sector unlocked via ENM API. UEs self-connect via SIB broadcast. Doubles site capacity. Effect in 3–8 minutes.
Applies: Crowd surge peaks, degradation. Not flash events — too slow
R5 — QoS Throttle
Video streaming deprioritised via PCF policy. VoLTE and signalling fully protected. Fastest resolution — effect in under 10 seconds.
Applies: Flash events (primary). Not crowd surge or degradation — wrong root cause
R6 — Inter-RAT Steering
5G-capable UEs steered from LTE to NR cell via SON engine. 290 UEs per cycle. Effect in 1–3 minutes.
Applies: Crowd surge, flash events. Not degradation — same degraded antenna serves NR
